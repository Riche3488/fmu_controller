# UI 개편 설계 — 안내형 작업공간, 목적함수 설계 도구, 시각화 작업대

## 왜

사용자가 겪는 문제 (사용자 발언 기준):

1. **어디서부터 시작해서 어떻게 진행해야 할지 막막하다.** 메뉴가 기능별(FMU/목적함수/프리셋/잡)로 흩어져 있어 "FMU 등록 → 기록 변수·리소스 → 목적함수 → 배치/최적화 → 결과" 순서를 사용자가 머릿속으로 맞춰야 한다.
2. **목적함수 작성이 난해하고 호환성을 확인하기 어렵다.** 빈 편집기에서 `evaluate(result, params)`를 직접 짜야 하고, 결과 DataFrame에 어떤 컬럼이 있는지는 run을 골라야 구석에 보인다. 이 코드가 어떤 잡의 run들과 맞는지 미리 알 수 없다.
3. **목적함수를 설계하기 위한 도구가 없다.** 대표 예: *"특정 신호값이 나온 이후부터 해석 종료까지 이동한 직선 방향 거리"*. 신호를 보며 트리거·구간·계산을 고르는 도구가 필요하다.
4. **시각화가 부족하다.** subplot으로 여러 플롯을 배치하는 등, 가능한 한 많은 시각화를 원한다.

성공 = 처음 쓰는 사람이 홈에서 안내만 따라가 FMU 하나로 결과 분석까지 도달하고, 위 예시 목적함수를 코드 없이 만들어 호환성까지 확인할 수 있다.

## 사용자가 정한 것

- **앱 구조: 홈 대시보드 + FMU별 단계형 작업공간 (안 C).**
- **목적함수 빌더 블록 4종 모두**: 트리거, 구간, 계산, 파생 신호.
- **시각화 작업대**: 아래 목록의 차트 전부. 3D용 `echarts-gl` 의존성 추가 허용.
- **분위기: 엔지니어링 콘솔 (안 A).** 다크 기본(라이트 전환 가능), 높은 정보 밀도, 시안 포인트 컬러, 숫자는 고정폭.

## 목표 / 비목표 / 안티골

목표
- 홈에서 현재 상태와 "다음 할 일"이 보이고, FMU 작업공간에서 단계 진행이 항상 보인다.
- 목적함수를 GUI로 설계 → 실제 run 신호 위에서 미리보기 → Python 코드 생성.
- 목적함수 ↔ 잡 호환성(필요 컬럼이 기록됐는지)을 저장 전에 확인.
- subplot 격자형 시각화 작업대, run 선택 연동, 레이아웃 저장.

비목표
- 새 시뮬레이션·최적화 기능, 백엔드 실행 엔진 변경.
- 다중 사용자, 원격 접속.
- 빌더로 모든 목적함수를 표현하는 것 (표현 못 하면 코드 모드로 쓴다).

안티골 (기술적으로 돌아가도 실패)
- 기존 기능(배치, 최적화, 프리셋, 리소스 variant, 잡 모니터, 결과 표·CSV)이 사라지거나 찾기 어려워짐.
- **목적함수 값을 DB에 저장**하게 됨 (CLAUDE.md 규칙 위반). 빌더 미리보기 값도 저장하지 않는다.
- 목적함수가 평범한 `.py`가 아니게 됨 — 빌더가 만든 것도 서버에서는 기존 `evaluate(result, params)` 코드로 그대로 실행돼야 한다.
- 오프라인에서 깨짐 (로컬 전용 앱: 폰트·라이브러리는 번들, CDN 금지).

## 제약

- 스택 유지: React 19 + Mantine 7 + ECharts 5 + Monaco + React Query, 백엔드 FastAPI. `schemas.py` ↔ `types.ts` 형태 일치.
- `ApiClient`에 메서드를 추가하면 `http/`와 `mock/` 둘 다 구현.
- 프론트 테스트는 mock client로 렌더 (`src/test/render.tsx`), 버그 수정은 재현 테스트 동반.
- 코드 주석·UI 문구는 한국어. 백엔드 CRLF 유지.

## 2. 앱 구조

### 홈 대시보드 (`/`)
- FMU 카드 목록: 모델명, 진행 상태(단계별 완료 여부), **다음 할 일 버튼 1개**(예: "기록 변수 고르기", "목적함수 설계하기", "배치 실행", "결과 보기").
- 실행 중/최근 잡 요약(진행률), 최근 결과 요약.
- 처음 사용(FMU 0개)일 때: 시작 가이드 체크리스트 + FMU 업로드 드롭존.

### FMU 작업공간 (`/fmus/:fmuId/...`)
상단 단계 바: **① 모델 → ② 변수·리소스 → ③ 목적함수 → ④ 실행 → ⑤ 결과 분석**. 각 단계 완료 표시와 "다음 →" 버튼.

| 단계 | 내용 (기존 페이지 재배치) | 완료 판정 (빌더 판단) |
|---|---|---|
| ① 모델 | FmuDetailPage의 메타데이터·변수 목록 | FMU 등록됨 = 항상 완료 |
| ② 변수·리소스 | 리소스 후보/variant (ResourcesPanel). 기록 변수 기본값은 ④에서 고름 — 여기서는 안내만 | 확인만 하는 단계라 방문 시 완료로 표시해도 됨 |
| ③ 목적함수 | 전역 목적함수 목록을 **이 FMU 기준 호환성**과 함께 표시, 새로 설계/편집 진입 | 호환 목적함수 ≥ 1 |
| ④ 실행 | 배치/최적화 탭 (기존 BatchSetup/OptimizationSetup + 프리셋 메뉴) + 이 FMU 잡 목록 | 잡 ≥ 1 |
| ⑤ 결과 분석 | 시각화 작업대 + 기존 결과 표 | 성공 run ≥ 1 |

- 좌측 사이드바: FMU 목록(빠른 전환), 그 아래 공용 메뉴(목적함수 라이브러리, 프리셋, 잡 전체).
- 기존 라우트(`/fmus/:id/batch`, `/optimize`, `/results`, `/jobs/:id`, `/objectives/:id`)는 유지하거나 리다이렉트해 깨진 링크가 없게 한다.

## 3. 목적함수 설계 도구

### 화면
- 좌측: 블록 설정 패널 (파생 신호 → 트리거 → 구간 → 계산 → 후처리), 현재 값과 필요한 컬럼 목록.
- 우측: **미리보기 run**(이 FMU의 성공 run 중 선택) 신호 그래프. 트리거 시점 세로선, 구간 음영, 계산에 쓰인 점/Δ 표시. 관련 신호마다 subplot 하나.
- 하단 우측: 호환성 요약, "여러 run에 일괄 적용" → 값 히스토그램 + 오류 목록.
- 하단: 생성된 Python 코드 (접힘, Monaco 읽기 전용). "코드로 직접 편집" 누르면 고급 모드로 전환.

### 블록
- **파생 신호**: 이름 + 수식 (`sqrt(x**2+y**2)`, `v*3.6`). 수식은 컬럼명·numpy 함수(sqrt, abs, sin, cos, exp, log, diff 등 허용 목록)만. 여러 개 가능, 이후 블록에서 일반 신호처럼 사용.
- **트리거**: 처음/마지막 상승교차·하강교차(임계값), 특정 시각, 신호 최대/최소 시점, 조건이 N초 이상 유지된 첫 시점. 트리거가 없으면 오류 메시지(값 없음)로 처리.
- **구간**: 전체, 트리거~종료, 시작~트리거, 트리거1~트리거2, 트리거±N초, 조건이 참인 모든 구간(합집합).
- **계산**: 끝값−시작값, 적분(사다리꼴), 평균, RMS, 최대, 최소, 표준편차, 구간 길이(초), 오버슛(%), 정착시간(허용오차 %), 두 신호 RMSE.
- **후처리**: 절댓값, 부호 반전, 배율.
- 임계값·배율·파생 신호 수식에는 숫자 대신 run 파라미터(`params["k"]`)를 쓸 수 있다. *(내 판단)*

예시 목적함수: 트리거 = `AccelPedal` 처음 ≥ 0.9 상승교차, 구간 = 트리거~종료, 계산 = `x` 끝값−시작값 (또는 `v` 적분).

### run이 아직 없을 때 (사용자 결정: 시험 실행)
- 이 FMU에 성공 run이 없거나, 고른 신호를 기록한 run이 없으면 ③에서 **"기본값으로 시험 실행"** 버튼을 보여 준다.
- 기존 `createBatch`로 run 1개짜리 배치를 제출한다: 파라미터 없음(기본값), sim = FMU `defaultExperiment`, `recordVariables` = 빌더가 필요로 하는 컬럼(+사용자가 추가로 고른 신호). 잡 이름은 `시험 실행 <시각>` 같은 식으로 구분.
- 잡 진행을 구독하고 끝나면 그 run을 미리보기 run으로 자동 선택. 백엔드 변경 없음.
- 호환성은 run/잡이 없을 때 FMU 변수 목록 기준(해당 이름의 변수가 존재하는지)으로 "기록 가능" 여부를 보여 준다.
- 시험 실행 잡도 ④ 잡 목록에 정상 잡으로 남는다 (숨기지 않음). *(내 판단)*

### 저장 형식
- 빌더 설정은 생성 코드 맨 위 주석 한 줄에 JSON으로 넣는다: `# fmuc-builder: {...}`. DB 스키마 변경 없음, 목적함수는 평범한 `.py`.
- 편집기를 열 때 이 주석이 있고 코드 본문이 설정에서 다시 생성한 것과 같으면 빌더 모드, 다르면 고급(코드) 모드. 고급 모드에서 빌더로 돌아가면 코드 수정이 사라진다는 확인을 받는다.
- 코드 생성은 **프론트엔드 순수 함수**(`lib/objectiveBuilder.ts`)로 하고, 미리보기 계산도 같은 설정을 **TypeScript로 평가**해 즉시 반응하게 한다. 저장된 코드의 최종 값은 기존 백엔드 평가가 기준이다. 일치 보장: 같은 설정에 대해 TS 평가와 생성 Python 코드의 결과를 비교하는 테스트(백엔드 테스트에서 생성 코드 fixture 실행)를 둔다.

### 호환성
- 필요 컬럼: 빌더 설정이면 설정에서, 코드 모드면 코드 안 `result["..."]` / `result['...']` 문자열 리터럴 추출(최선 노력, "추정"으로 표시).
- 판정: 이 FMU의 잡별 `config.recordVariables`(+`time`)와 비교 → 잡별 OK / 누락 컬럼 목록. 순수 함수 `lib/compat.ts`.
  - `recordVariables`가 빈 목록이면 FMPy 기본값(출력 변수 전체)이므로 FMU의 `causality=output` 변수 목록과 비교한다. *(내 판단)*
  - 누락 컬럼이 있으면 "④ 실행에서 기록 변수에 추가하세요" 안내와 함께, ④ 폼에 해당 변수를 미리 넣어 주는 링크를 단다. *(내 판단)*
- 목적함수 라이브러리와 ③ 단계 목록에 호환 배지 표시.

### 일괄 테스트 (백엔드 추가)
- `POST /api/objectives/test-batch` `{code, runIds[≤200]}` → run별 `{value, error, durationMs}`. 기존 `Evaluator`를 그대로 사용, 값은 저장하지 않음.
- `ApiClient.testObjectiveBatch` 추가 (http + mock).

## 4. 시각화 작업대 (⑤ 결과 분석)

### 틀
- 상단: 데이터 범위 필터(잡, variant, 상태, 목적함수 — 기존 ResultsPage 필터 재사용), 레이아웃 선택(1×1, 1×2, 2×2, 2×3, 3×N 또는 자유 추가), 시간축 줌 동기화, 레이아웃 저장/불러오기, 패널 추가.
- 패널: 제목, 차트 종류 선택, 데이터 매핑(x/y/색/크기/그룹/변수), 패널별 PNG·CSV 내보내기, 최대화.
- **선택 연동**: 어느 패널에서든 run을 클릭/브러시 선택하면 모든 패널에서 강조, 시계열 패널은 선택 run을 그린다. 선택 목록은 결과 표와 공유.
- 레이아웃 저장: 프리셋에 `kind: 'dashboard'` 추가 (설정 = 격자 + 패널 정의, 변수/목적함수는 이름으로 참조). 백엔드 `presets.py`의 kind별 스키마 검사에 추가. 기존 프리셋처럼 `sourceFmuId`를 기록하고, 다른 FMU에서도 불러올 수 있되 없는 변수·목적함수를 참조하는 패널은 "찾을 수 없음" 상태로 표시한다. *(내 판단)*
- 데이터 규모: 기존 ResultsPage처럼 `listRuns(limit=100000)`으로 범위 전체를 받아 클라이언트에서 계산한다. 별도 집계 API는 만들지 않는다. *(내 판단 — 수천 run 규모 기준)*
- 기존 결과 표(RunTable)·CSV 내보내기는 작업대 아래 또는 탭으로 유지.

### 차트 목록
run 단위 값 (파라미터·목적함수)
- 산점도 (색·크기 매핑), 산점도 행렬, 평행좌표, 히스토그램, 박스/바이올린 (잡·variant별), 상관 히트맵, 레이더 (선택 run 비교), 막대 (variant 비교)

응답면·민감도
- 2D 등고선/히트맵 (파라미터×파라미터 → 목적함수, 격자 보간), 토네이도 (순위 상관 기반 민감도), 1D 슬라이스, 3D 산점도/표면 (`echarts-gl`)

최적화 전용
- 수렴 이력 (run index 순 best-so-far), 파레토 프런트 2D/3D (기존 `lib/pareto.ts`), 파라미터 중요도 (|Spearman| 기반 — Optuna 내부 기능 사용 안 함), trial 개요 (index별 소요시간·성공/실패 막대 — Run에 시작/종료 시각이 없어 실제 타임라인 대신, DB 변경 없음) *(내 판단)*

시계열 (`getTimeseries`)
- 공유 시간축 subplot, 여러 run 겹쳐 그리기 (파라미터 값으로 색 그라데이션), 평균±범위 밴드, 기준 run 대비 차이, XY 위상도, FFT 스펙트럼

- 통계·보간·FFT·상관은 `lib/` 순수 함수 + 단위 테스트.
- 시계열을 많이 겹칠 때는 run 수 상한(빌더 판단, 예: 50)과 `maxPoints`로 다운샘플.

## 빌더에게 맡기는 것

- 컴포넌트 분해, 파일 배치, 정확한 색 값·간격.
- 홈의 "다음 할 일" 문구와 우선순위 규칙.
- 2D 등고선 보간 방식, FFT 구현, 바이올린 커널 폭.
- 차트별 세부 옵션의 범위.

## 구현 순서

1. 테마 + 앱 구조 (홈, 작업공간 단계 바, 기존 페이지 재배치)
2. 목적함수 설계 도구 (빌더, 코드 생성, 호환성, 일괄 테스트 API)
3. 시각화 작업대 (틀·연동·레이아웃 저장 → 차트군 순차 추가)

각 단계 끝에 `pytest`, `npm test`, `npx tsc -b`, `npm run lint` 통과.
